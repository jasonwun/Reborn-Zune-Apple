# M15.1 — macOS responsive model v2: screen-fixed sizes, window-driven arrangement

Status: planned · Owner: yjd · Supersedes the macOS half of `M15.md` (the
continuous window-width scale). iPad / tvOS behavior is untouched and the
M13/M14 bucket tables stay bit-identical.

## Background

M15 shipped a continuous scale: every font / spacing / cover / chrome size
multiplies by `windowScale = clamp(windowWidth / 1440, 0.75, 1.15)`. It works
mechanically, but owner's review (2026-09-27) rejected the model:

> 字和空间的大小应由**屏幕硬件分辨率**决定、基本恒定；窗口大小变化只改
> 变元素的**位置/排布**（重排、换列、显隐、滚动），不整体缩放。

Think Apple Music: drag the window and the layout reflows; nothing zooms.

M15.1 also folds in the MiniPlayer pinning fix (already implemented during
review): on macOS the bottom player is a `safeAreaInset`, so shrinking
window height compresses the content area instead of pushing the player
off-canvas.

## Model

### Size tokens — fixed per screen (macOS)

`ResonantLayout.mac(screen:)` derives all scale tokens **once** from the
hardware screen the window is on:

```
scale = clamp(screenWidth / 1440, 0.9, 1.15)   // 1512-pt screen → 1.05
windowScale      = scale
displayFontScale = scale
textScale        = min(scale, 1.1)             // body text ramps gently
```

Tokens do NOT change when the window resizes. They change only when the
window moves to a different screen (re-evaluated on screen change) — and on
screens that need it (external 1080p vs 5K), not mid-drag.

### Window size — arrangement only

A new environment value `resonantWindowSize: CGSize` is published by the
root `GeometryReader`. Views read it to make **discrete layout decisions**;
they must not multiply sizes by it. Reflow rules:

| Screen | Rule |
| --- | --- |
| Albums / Artists / Playlists / Search grids | `.adaptive(minimum:)` with **fixed** (screen-scaled) minimums — column count follows window width for free |
| Home panorama | Width ≥ 1200: full panorama (title left, peek strip right). 900–1200: peek strip drops to a single column. Height < content: the pick panel scrolls internally; PivotNav and MiniPlayer stay pinned |
| Album / Artist / Playlist detail | Header keeps fixed metrics; track list always scrolls; below 1000pt width the header's trailing column stacks under the leading column |
| NowPlaying | Two-axis reflow: width ≥ 1000 keeps the horizontal split; below that art stacks above controls. All controls always on-canvas at the 900×600 floor |
| PivotNav / MiniPlayer | Fixed metrics. MiniPlayer hides the up-next block below 1100pt width |

The 900×600 window floor stays. If a composition cannot honestly fit at the
floor even after reflow, the content area scrolls — sizes never shrink below
the screen-fixed tokens.

## Acceptance criteria

1. Dragging the window edge changes no font size, spacing, cover frame, or
   control size — only arrangement (visual sweep at 900 / 1100 / 1440 /
   1512 widths, all five screens).
2. Moving the window between screens of different resolutions re-derives
   the tokens once (code path exists; manual verification noted if only
   one screen is available).
3. MiniPlayer remains fully visible at every legal window size, including
   wide-but-short (e.g. 1440×620) and the 900×600 floor.
4. Grids gain/lose columns as the window crosses cell-width multiples,
   with fixed cell minimums.
5. At 900×600 every screen renders without clipped text, truncated meta
   lines, or controls leaving the canvas (regression of M15 R1 defects
   stays fixed).
6. iPad / tvOS: bucket tables and renders bit-identical; both simulator
   builds green.
7. `swift build`, `swift test` (updated ResonantLayoutTests lock the new
   token formulas), `xcodegen generate`, and all three `xcodebuild`
   targets exit 0.

## Evidence rules

Same as M15: canonical builds + tests, plus a resize sweep. External
CGWindowList probes are ×0.9 off on this host (see
`reports/M15_evaluator_R2.md`) — in-process AppKit frames are the window
ground truth. Screenshots come from the NSWindow-hosted renderer, not
ImageRenderer (blank scroll regions).
